Evidence

Grounding Context

Codebase context. Stackward is a single-module Android client (:app, Kotlin + Compose, dev.stackward) with no backend. The stated job is a fast “what’s wrong right now” from a phone, without a laptop and without sending logs to SaaS. The architecture is “the model proposes, the human disposes”: Gemma E2B/E4B via MediaPipe emits structured JSON, never raw shell; a three-tier PermissionEngine plus hardware Keystore and biometrics gates writes. Phases 0–5 are scaffolded (TOFU, jump-host, Proxmox client, log parsing, one-timer sudoers). The app already degrades to raw logs and heuristic digests if no model file is imported. There is no STRATEGY.md or CONCEPTS.md. Canonical constraints live in PRD.md and README.md. The README also calls this a personal infrastructure tool, MIT-licensed, not ready for external contribution.

Pain points that bear on need and realism. First useful loop currently requires three independent carries: an ADB/Play-Protect install path, a user-imported multi-gigabyte .task/.litertlm file on a 4–6 GB RAM phone, and an out-of-band root bootstrap the app is forbidden to run. Quantized 2B/4B models are assumed to hallucinate, so mutating UI must show the literal command. Android 2026 developer verification already breaks Chrome sideload; the committed dogfood keystore is not for Play.

Past learnings. None — docs/solutions/ does not exist.

External context (2026). Managing Proxmox/Docker/Linux from a phone is a settled daily workflow: Tailscale + Termius/Mosh, the official Proxmox Flutter app, Pulse (~6.5k GitHub stars; Community free; Relay ~$39/yr; Pro ~$79/yr with Patrol AI). The open slice is natural-language plus gated actuation, and it is filling on the host (Pulse Patrol, HolmesGPT, Grounder), not on the handset. Pulse Patrol’s own local bar is roughly an 8B with reliable tool calls on ~8 GB VRAM. Gemma 4 E2B is fast enough on 2026 flagships (~52 tok/s on an S26 Ultra) and is in a different size class from that bar. Homelab surveys put fun ahead of privacy; willingness to pay is FOSS-shaped. Home Assistant Companion is the topology that already won this audience: thin trusted phone, brain on the LAN. Cloud chat pasted into Termius is the zero-install quality foil. Android developer verification begins 30 Sep 2026 in participating countries and goes global in 2027; hobbyist limited distribution is about 20 devices.

Slack context. Not requested. Dedicated Slack research tools were not used.

Directions

Ranked Ideas

1. Name the fork 2. Estate-local brain 3. Personal lookout 4. Notary, not Gemma 5. 2026-installable client 6. N=1 MIT success

1. Name three mutually exclusive theses — then pick one

1 axis: competitive-wedge confidence: 88% complexity: Low
Description
The “is there a need / is it realistic / should I continue” question is unanswerable while one APK claims four products at once: on-device Gemma SRE, a privacy-preserving lookout, a biometric notary for SSH, and a small-business operator tool. Write a short STRATEGY.md that lists three mutually exclusive north stars and chooses exactly one. Mixing them is why the PRD can be both true and directionless.
Axis
competitive-wedge
Basis
direct: The PRD user sentence is “what’s wrong right now” without a laptop or SaaS (PRD.md users section) while invariant 1 is “inference stays on-device,” Maintain is a v1 capability, Provision is a future pack, and the README still calls this a personal MIT tool. Those claims cannot all be the reason the project exists. reasoned: A go/no-go is a choice among theses, not an average of them. Pulse already occupies “permissioned AI for Proxmox”; Termius occupies “SSH from a phone.” Stackward only has a need if it names the leftover job and drops the rest as non-goals.
Rationale
This is the move that changes what you do next even if you never write another line of Kotlin. Ideas 2–4 below are the three honest “yes, continue” paths. Idea 5 is the shipping constraint that applies to all of them. Idea 6 is the audience constraint. Until one thesis is named, more phases will keep compounding a mixed identity.
Downsides
Choosing feels like killing work already scaffolded (MediaPipe, Maintain packs, SMB copy). That sunk cost is real. The cost of not choosing is larger: you cannot tell whether the project is succeeding.

2. Phone as trusted remote; brain on the estate

2 axis: inference-locus confidence: 76% complexity: High
Description
Keep the privacy product (“no third party sees logs or keys”) and the phone-resident disposer (Keystore, biometric, literal command, one-timer sudoers). Retire “Gemma must live in the handset” as an always-true invariant. Inference becomes operator policy: none, on-device if the phone can, or on a user-owned process the existing SSH session already reaches. That is the Home Assistant Companion topology applied to Proxmox/Docker, and the shape a larger team would build for this job in 2026.
Axis
inference-locus
Basis
direct: Invariant 1 currently freezes locus: “Inference stays on-device (local brain)” and the decision table assigns “Where intelligence runs” to Product / on-device. The privacy sentence underneath is different: no prompts, logs, or command output leave the device except over the user’s own SSH/API. external: HA Companion already won “thin trusted phone, brain on LAN.” Pulse Patrol, HolmesGPT, and Grounder put NL + gated actuation on the host; Pulse’s local bar is an 8B with tool calls, above phone E2B/E4B. reasoned: Credential residency is what homelab privacy actually buys. Token generation on an NPU is a capability tax (RAM, import, no emulator, weak tool-calling). Unlocking locus keeps Stackward’s identity as a phone agent for your infra without requiring MediaPipe to out-reason Patrol.
Rationale
Need for “what’s wrong / act from the pub, nothing to SaaS” is real. The unrealistic part of the current direction is asking a 2B/4B phone model to be the SRE. This fork says: the category is right; the 2026 implementation that can meet the job is companion-shaped. A basis verifier called this subject-replacement because the PRD assigns locus to Product. That citation describes the current freeze; it does not forbid changing the freeze. An architectural pivot inside the same product is in bounds.
Downsides
You give up the rarest claim (“inference never leaves the SoC”). You may add a user-run host helper, which the current “APK plus your infra, no compose” story treated as a boundary. Quality then depends on whatever the operator can run on the node. iOS still sits outside this Android client.

3. Personal lookout: triage-only, model-optional, digest tempo

3 axis: job-to-be-done confidence: 84% complexity: Medium
Description
Collapse v1 to the job the PRD actually wrote in the user sentence: a ridge lookout, not a sheriff. Read-only logs, status, Proxmox/Docker views, heuristic (then optional NL) digests on a correspondence cadence. Maintain and Provision go dark. Gemma is a plugin, not the title. Success is “I glanced at the phone and knew whether to open a laptop,” not “I SRE’d from the pub.”
Axis
job-to-be-done
Basis
direct: Users “want a fast way to ask ‘what’s wrong right now’ from their phone without opening a laptop or exposing infra to a third-party SaaS monitoring tool.” Capability packs already encode Monitor / Maintain / Provision, with Provision denied in v1. No-model mode already shows raw logs; DigestAnomalyDetector flags issues with “v1 — no ML required.” external: Fire lookouts, physician pagers, and HA “something is on fire” notifications won by making the commute decision cheap. Official Proxmox app and Pulse already fight over actuation dashboards. reasoned: A 2B model behind literal-command confirm is slower than Termius for people who already know the restart. The lookout job does not need that fight.
Rationale
This is the most realistic “yes, continue” if you are the user. The scaffold already does most of it. It answers need without requiring Gemma to beat Pulse Patrol, and it answers realism without a host-side brain. Combined with idea 6, it is a coherent personal instrument.
Downsides
You will feel like you shipped a log viewer. Maintain code and the propose/dispose slogan look orphaned. If the real itch was signing a reboot without a laptop, lookout under-serves that itch (see idea 4).

4. The invention is the notary, not Gemma

4 axis: competitive-wedge confidence: 80% complexity: Medium
Description
Compete on the ritual that cloud-paste and Termius skip: exact command string, face unlock, time-bounded one-timer sudoers, then the extra guns come off. Treat PermissionEngine as the product and Gemma as an optional clerk who may only point at a closed verb catalog (reboot_vm, restart_service, fetch_journal). The model does not mint free-form shell. Success metric: time from a known fault to a biometric-confirmed catalog action — not summary quality versus GPT.
Axis
competitive-wedge
Basis
direct: “The model proposes, the human (or a narrow, pre-approved rule) disposes.” Architecture Tier 2 blocks until the user confirms the exact command string. The risk table already assumes a small model will hallucinate a plausible destructive command, and mitigates by showing the literal string. PermissionDecision.DraftOnly exists for boundary changes. reasoned: A notary does not advise on the deal; they make the signature the signature. Letters of marque beat a standing navy when you cannot afford always-on elevation. Pulse Patrol is a capable lawyer with tools on the ward. Stackward can be the commission, not the better brief. Closing the verb catalog is the architectural version of the hallucination table, rather than hoping UI confirm catches a bad JSON command field.
Rationale
This is the distinctive leftover after conceding NL quality. If Pulse Patrol ran on the node tomorrow, “I will not execute text I did not see, under a key I did not unlock, as an identity that cannot silently grow sudo” is still a reason to keep building. It also survives deleting MediaPipe.
Downsides
A closed catalog is less “agentic” and may feel like a thin Proxmox/systemd remote. You still need the host helpers for one-timers. If operators already type the restart faster in Termius, the notary is ceremony without time saved — then this thesis fails in dogfood, which would be useful information.

5. Ship a 2026-installable client; treat Gemma as an expert extra

5 axis: feasibility-distribution confidence: 75% complexity: Medium
Description
Make the default artifact something a stranger can install without ADB, a 2.6 GB Hugging Face hunt, or a root bootstrap. That means a small (possibly native-lib-free / smoke-shaped) viewer-plus-gates client on a verified-developer path, with Gemma remaining the dogfood SKU. Version the host contract so Monitor works on key-install-only; bootstrap becomes power-user, not the door to first digest. Either enroll in Play / Android developer verification or write “~20 devices” as an explicit ceiling.
Axis
feasibility-distribution
Basis
direct: docs/INSTALL.md already says not to rely on Chrome “Open APK → Install” because developer verification / Play Protect rejects sideloaded APKs; ADB is the reliable path. Model files are user-imported, not bundled. scripts/bootstrap_linux.sh states the app does not run it and that it requires root. A smoke flavor already exists as an install probe. external: Android developer verification starts 30 Sep 2026 (participating countries) and is planned global in 2027; hobbyist limited distribution is about 20 devices. reasoned: A needed product that cannot be installed is a lab. The PRD’s “enter IP → first digest in under five minutes” cannot include three laptop-side carries and still be a phone product.
Rationale
This is the realism test that applies no matter which thesis you pick. If you will not become a verified publisher, idea 6 (N=1) is not a consolation prize — it is the only honest audience. If you will ship to homelabbers, distribution is the next product, not a footnote after Phase 6.
Downsides
Play review of an SSH/Keystore agent is a threat-model and policy project of its own. Splitting SKUs adds maintenance. Key-install-only Monitor is a weaker demo than the full bootstrap loop.

6. Declare N=1 MIT success; stop writing a market you cannot reach

6 axis: audience-wtp confidence: 70% complexity: Low
Description
Strike “small businesses” / “small teams” from the user sentence until a second-device story exists. Write success as “this phone, this cluster, travel days without a laptop.” Homelab willingness to pay is FOSS-shaped; Pulse already charges for reach and governed AI. Under current invariants there is no path to a million users that does not violate no-cloud or become Pulse. That is not a failure if the builder is the user.
Axis
audience-wtp
Basis
direct: Non-goal: no multi-user / team accounts — single operator, single device. LICENSE is MIT. README: “Not yet ready for external contribution — this is a personal infrastructure tool.” The users section still names homelab users and small businesses together. external: Self-host surveys: most people host for themselves; fun outranks privacy; paid analogs in this niche are convenience (Pulse Relay/Pro, Termius Pro), not another SSH client. reasoned: Flip to N=1 and ADB plus bootstrap are the correct channel. Flip to 1M and you need Play, iOS, support, and a model distribution story the privacy invariant forbids. Do not hold a quiet belief that dogfood becomes a company.
Rationale
The founder question “is there a need?” has two answers. Need-for-you: yes, if you actually open this instead of Termius. Need-as-a-market: weak, and already served. A verifier called this below a meeting-test because teams are already a non-goal. Keep it anyway: the PRD still writes SMB into the aim, and that sentence is what makes “should I go this direction” feel like a startup question.
Downsides
Naming N=1 can become an excuse never to dogfood the install path. It also closes a door you might want later. The discipline is to mean it: if you do not miss the app when traveling, stop.
